- **근거** 실행계획 v1.8.2 · 05_프론트첨삭 항목 1 (W0 스파이크① 1일, G1 판정 기준 포함)
- **대상 요구사항** F-CRP-01a ★긴 원본 뷰어 (P0 · must · MVP)

---

## 목적

요구사항정의서 v2.3 `F-CRP-01a`의 수용 기준 3개가 브라우저에서 실제로 성립하는지 확인합니다.

> ① 10,000px 원본에서 스크롤이 끊기지 않음
> ② 크롭 좌표가 원본 픽셀 기준으로 저장됨
> ③ 확대·축소 후에도 좌표가 어긋나지 않음

W3(9/7) 구현 중에 "브라우저에서 안 되는 구조였다"를 발견하면 대안을 짤 시간이 없기 때문에
W0에 앞당겨 검증합니다.

## 구현 범위

**만든 것**

- `/spike/crop-viewer` 검증 화면 — 긴 이미지 뷰어, 줌(0.1~4배), 드래그 크롭, 다중 크롭,
  크롭 선택·삭제, source 좌표 목록, 개발용 HUD
- 좌표 변환 모듈 (`lib/spike/coordinates.ts`) — React·브라우저 API 없는 순수 계산
- 헤드리스 검증 스크립트 (`scripts/verify-coordinates.mjs`) — 87건
- 브라우저 자체 검증 패널 — 화면 안에서 DOM 실측값과 계산값을 비교
- 눈금 fixture 생성기 (`scripts/make-ruler.mjs`) — 라이브러리 없이 PNG 직접 생성

**만들지 않은 것** (스파이크 범위 밖)

OCR · 인페인팅 · 백엔드 저장 · 인증 · S3 캔버스 · 디자인 시스템 · 크롭 영역 재조정(리사이즈 핸들)

**추가한 라이브러리** 없음. 기존 스택만 사용했습니다.

### C. 성능 실측 — **미측정 (PARTIAL)**

| 검증 항목 | 결과 |
|---|---|
| 7,000px 스크롤 프레임 | **미측정** |
| 10,000px 스크롤 프레임 | **미측정** |
| 이미지 디코딩 시간 | **미측정** |
| overlay 다수 생성 시 지연 (NFR-05 100ms) | **미측정** |

**사유** — 이번 작업 환경(격리 리눅스 샌드박스)에 헤드리스 브라우저 실행에 필요한
시스템 라이브러리를 설치할 권한이 없어 실제 브라우저를 띄우지 못했습니다.
계산 로직은 브라우저 없이 전량 검증했으나, 스크롤 부드러움·디코딩 시간처럼
**실제 브라우저에서만 나오는 수치는 측정하지 못했습니다.**

**대안** — 화면 안에 [브라우저 자체 검증 실행] 버튼을 넣었습니다.
누르면 브라우저가 실제로 그린 위치(`getBoundingClientRect`)를 읽어
계산값과 비교하고 PASS/FAIL을 표시합니다. HUD에 이미지 로드 시간(ms)도 나옵니다.
아래 순서로 5분이면 C 항목을 채울 수 있습니다.

```
npm run dev
→ http://localhost:3000/spike/crop-viewer
→ 이미지를 10,000px 로 바꾸고 [브라우저 자체 검증 실행]
→ HUD 의 "이미지 로드" 시간과 결과 패널을 이 문서에 옮겨 적기
```

## 발견된 문제

실제로 발견된 것만 적습니다.

**1. `Date.now()` / `Math.random()`이 React 19 lint 규칙에 걸림**

`react-hooks/purity` 규칙이 이벤트 핸들러 안의 호출까지 오류로 잡았습니다.
증가 카운터(`useRef`)로 바꿨습니다. 실제 구현에서는 서버가 발급한 `pieceId`를 쓰므로
이 문제는 자연히 사라집니다.

**2. `next/image`를 쓸 수 없음**

줌에 따라 폭이 계속 변하는 초대형 이미지라 Next.js 이미지 최적화가 맞지 않습니다.
순수 `<img>`를 쓰고 lint 규칙을 해당 줄에서만 껐습니다.
S2 실제 구현에서도 같은 판단이 필요합니다.

**3. 부동소수점 잔차 2.84e-14 px**

`previewScale`이 무한소수(0.333333…)이고 줌이 4배일 때 나타납니다.
반올림 단계에서 사라지므로 실무 영향은 없습니다. 다만 좌표 비교에
`===`를 쓰지 말고 허용 오차를 두어야 한다는 뜻입니다.

**4. 성능 항목 미측정** — 위 C 항목 참조.

## 다음 단계 판단

> ### 현재 구조로 S2 구현 가능 (성능 실측 조건부)

**근거**

1. **좌표 정확성은 구조적으로 보장됩니다.** 저장값을 한 번도 덮어쓰지 않고
   화면 좌표를 매번 새로 계산하므로 drift가 발생할 경로 자체가 없습니다.
   87건 자동 검증이 이를 뒷받침합니다.
2. **`previewScale`과 `zoomScale` 분리가 실제로 동작합니다.**
   previewScale 0.5 fixture에서 원본 14,000px 좌표가 정상적으로 나왔습니다.
3. **Canvas나 전용 라이브러리가 필요하지 않습니다.**
   `<img>` + 절대 위치 overlay로 요구 기능이 전부 구현됐습니다.
   `react-zoom-pan-pinch`, `react-image-crop` 같은 라이브러리를 도입하면
   오히려 좌표계를 그쪽 규약에 맞춰야 해서 손해입니다.
4. **에러 케이스가 전부 한 함수(`buildCropFromDrag`)에서 처리됩니다.**
   S2 구현 시 UI만 바꾸고 이 함수는 그대로 씁니다.

**조건** — 아래 하나라도 실패하면 판단을 재검토합니다.

- 10,000px 이미지 스크롤이 눈에 띄게 끊김 → 이미지 분할 로딩 검토
- 크롭 20개 이상에서 드래그 지연 100ms 초과 (NFR-05) → overlay 렌더 최적화

경험상 1000×10000 PNG(60KB)는 문제되지 않을 크기지만, 실제 상품 상세페이지는
사진이 많아 수 MB가 되므로 **실제 원본으로 한 번 더 확인**하는 것이 안전합니다.
