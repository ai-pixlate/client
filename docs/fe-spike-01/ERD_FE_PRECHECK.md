## 항목 1. 텍스트 블록 소유 관계 — 확정됨

### 문서상 상태

`05_상태_정책 · PL-21 ★편집 데이터 3층 구조`에 명문화되어 있습니다.

```
크롭 (crop_id)          S2 생성 · 조각당 1개
 └ 배치 (placement_id)   S3 생성 · 조각:배치 = 1:N
    └ 텍스트 블록 (block_id)  S4 생성 · 배치:블록 = 1:N
```

`00_문서정보 · v1.9 변경 1`이 결정 근거까지 남겨두었습니다.

> 텍스트 블록의 소유자를 배치(placement)로 확정했다.
> 근거: ① 모듈이 둘이면 좌표가 두 벌 필요 ② 배치 배율이 다르면 폰트 크기가 달라야 함
> ③ 한쪽 배너 문구 수정이 다른 배너에 전파되면 사용자 기대에 어긋남.
> 중복 번역은 원문 해시 기준 번역 캐시로 방지한다.

### 현재 이해 (프론트)

| 층 | 담는 것 | 담지 않는 것 |
|---|---|---|
| **크롭** `crop_id` | 인페인팅 결과 · 마스크 · OCR 원본(줄 단위 텍스트·bbox·순서) · 폰트 속성 | **배치 종속 값 일체** (F-INP-01c 수용 ⑤) |
| **배치** `placement_id` | module_id · 모듈 내 위치 · 배율 · 겹침 순서 | 텍스트 (S3 시점에는 아직 없음) |
| **텍스트 블록** `block_id` | 원문 · 번역문 · 역할 · 번역 상태 · 모듈 좌표 | — |

**조각 A를 모듈 2곳에 배치하면** → 크롭 1건, 배치 2건, 블록 (덩어리 수 × 2)건.
한쪽 수정이 다른 쪽에 전파되지 않습니다 (F-CFM-02a 비고).

**Spike 시점에 새로 파악한 것** — 블록은 좌표 관련 키를 **두 개** 가집니다.

| 필드 | 의미 | 변하는가 |
|---|---|---|
| `placement_id` | **출처.** 어느 배치에서 나왔는가 | 안 변함 |
| `module_id` | **표시 위치.** 지금 어느 모듈에 보이는가 | F-TXT-08로 이동 시 변함 |

이 분리 덕분에 "블록을 다른 모듈로 옮겨도, 원 조각을 지우면 옮긴 블록도 함께 사라진다"
(F-TXT-08 수용 ③④, PL-22)가 성립합니다. 프론트는 **삭제 연쇄를 직접 계산하지 않고
서버 응답을 다시 받는 것으로 가정**합니다.

### 백엔드 확인 필요 여부 — 불필요

다만 대조는 필요합니다.

> **[대조]** PL-21의 3층 구조와 `block.placement_id` / `block.module_id` 분리가
> 실제 ERD 테이블에도 같은 형태로 들어갔는지 확인 부탁드립니다.
> 특히 블록이 `placement_id`와 `module_id`를 **둘 다** 갖는지가 F-TXT-08 구현의 전제입니다.

### MVP 범위 주의

`v2.1 변경 2` · `v2.3 변경 4`에 따라 **MVP에서는 삭제 연쇄가 발생하지 않습니다.**
전진 이동만 지원해 S3 이후 S2로 갈 수 없고, S2 체류 중에는 배치·블록이 아직 없기 때문입니다.
ERD의 CASCADE 제약은 12월 되돌림 대비로 유지하되, **MVP UI에 연쇄 삭제 경고를 만들 필요는 없습니다.**

## 항목 2. 좌표계 규약 — 대부분 확정, 필드명만 미정

### 확정된 것

| 항목 | 내용 | 근거 |
|---|---|---|
| 좌표계 3종 | source(원본 픽셀) / piece(조각 내부) / module(970×300) | data-spec 0-1 · F-INP-02 · F-INP-02c |
| 크롭 좌표 | **원본 좌표**로 주고받음. 프론트가 표시 배율을 역산해 변환 후 전송 | F-CRP-01a · data-spec 0-1 |
| 표시 배율과 저장 좌표 분리 | 명시적 요구사항 | F-CRP-01a |
| piece → module 변환 | **백엔드가 계산.** 배치 위치와 배율을 곱하며 AI가 개입하지 않음 | F-INP-02c |
| 조각 배율의 의미 | S3에서 정한 배율이 S4 좌표 변환 시 그대로 곱해짐 | F-PLC-02d (v2.2 명시) |
| OCR 수행 해상도 | 조각의 **원본 해상도** | F-INP-02 수용 ④ |
| 줄 단위 bbox | 별도 테이블 없이 `source_lines`(jsonb)에 보관 | F-INP-02a |

### 프론트 결론 (Spike①에서 검증 완료)

- **프론트 좌표 변환의 오차는 0입니다.** 87건 자동 검증 통과.
- 따라서 **NFR-13 / OI-27의 허용 오차 예산을 프론트에 배분할 필요가 없습니다.**
  OCR 인식 정확도와 조각→모듈 변환에 전부 쓰시면 됩니다.
- 상세 규약은 `COORDINATE_CONVENTION_DRAFT.md` 참조.

### 백엔드 확인 필요 — 3건

> **[Q-1] 좌표 필드명을 아래로 확정해도 되겠습니까?**
> `sourceX / sourceY / sourceWidth / sourceHeight`
> `pieceX / pieceY / pieceWidth / pieceHeight`
> `moduleX / moduleY / moduleWidth / moduleHeight`
> `x` 하나만 쓰면 어느 기준인지 알 수 없어 좌표 버그의 원인이 됩니다.
> (data-spec 0-1의 제안이며 v2.3에서 반박되지 않았습니다)

> **[Q-2] `previewScale`을 업로드 응답에 넣어 주실 수 있습니까?**
> 프론트가 `previewWidth / originalWidth`를 직접 계산하면 이미지 디코딩 타이밍에 따라
> 값이 달라지고 1~2px씩 어긋납니다. 백엔드가 다운스케일을 수행하므로
> 정확한 값은 그쪽에만 있습니다.
> 필요 필드: `originalWidth`, `originalHeight`, `previewUrl`, `previewScale`, `originalUrl`

> **[Q-3] OCR 결과의 `bbox`는 어느 좌표계입니까?**
> `F-INP-02`는 조각의 원본 해상도에서 인식한다고 하므로 **piece 좌표**로 읽었습니다.
> `source_lines` 안의 줄 단위 bbox도 같은 기준인지 확인 부탁드립니다.
> 블록에는 piece 좌표와 module 좌표가 **둘 다** 내려오는 것으로 가정하고 있습니다 (data-spec 0-1).

## 항목 3. 대용량 원본 업로드 경로 — 미확정 · 가장 시급

### 문서상 상태

**업로드 경로를 규정한 문서가 없습니다.** 관련 조항은 두 개뿐입니다.

| 근거 | 내용 | 업로드 경로를 정하는가 |
|---|---|---|
| `PL-07` 원본 데이터 보관 | 업로드 원본·크롭 조각·인페인팅 배경·결과물을 **오브젝트 스토리지**에 보관 | 아니오 (보관 위치만) |
| `NFR-20` 보안 | 업로드 파일은 암호화 저장하고 **서명 URL로만 접근** | 아니오 (읽기 접근만) |

`API_SPEC.MD`는 F-ACC 계정 영역만 작성되어 있어 업로드 엔드포인트가 없습니다.
`F-SRC-01`도 UI 동작(드래그앤드롭·다중·재정렬)만 규정합니다.

### 문제

프론트는 Vercel에 배포될 예정입니다. **서버리스 함수의 요청 본문 제한은 약 4.5MB**입니다.

| 조건 | 값 |
|---|---|
| 처리 대상 | 세로 수천~수만 px 원본 (F-CRP-01a) |
| 검증 기준 | 긴 변 최대 10,000px (F-CH-05a) |
| 실제 상품 상세페이지 | 사진 다수 포함 시 수 MB ~ 수십 MB |
| MVP 업로드 | **다중 업로드** (F-SRC-01) |

원본 1장이 4.5MB를 넘으면 Next.js API Route를 경유하는 업로드는 **실패합니다.**
파일 1개만으로도 초과할 수 있고, 다중 업로드면 확실히 초과합니다.

### 제안하는 구조

```
FE  →  API 에 업로드 URL 요청       POST /uploads/presign
    ←  presigned URL 발급           { uploadUrl, fileId, expiresAt }
FE  →  스토리지로 직접 PUT          (Next.js 서버를 경유하지 않음)
FE  →  업로드 완료 통보             POST /jobs/{jobId}/source-images { fileId, order }
    ←  { sourceImageId, originalWidth, originalHeight,
         originalUrl, previewUrl, previewScale }
```

이 구조의 이점

1. 파일 크기 제한이 사라집니다 (스토리지로 직접 감).
2. `NFR-20`(서명 URL 접근)과 자연스럽게 맞습니다.
3. 다운스케일·크기 측정을 백엔드가 하므로 `previewScale`이 정확해집니다 (Q-2와 같은 답).

### 백엔드 확인 필요

> **[Q-4 · 최우선] 원본 업로드를 presigned URL 직접 업로드로 가도 되겠습니까?**
> Vercel 서버리스 요청 본문 제한(약 4.5MB) 때문에 API Route 경유는 원본 1장으로도
> 초과할 수 있습니다. 나중에 발견하면 업로드 관련 코드를 전면 수정해야 합니다.
> 8/26 S1~S3 스키마 확정에 이 결정이 포함되어야 합니다.

> **[Q-5] `previewUrl` 생성 시점은 언제입니까?**
> 업로드 완료 통보에 대한 동기 응답입니까, 아니면 비동기 처리 후 폴링해야 합니까?
> 후자라면 S1→S2 이동 시 "프리뷰 생성 중" 화면이 필요합니다.
> (S2 진입 조건이 달라지므로 화면 설계에 영향이 있습니다)

## 부수 확인 항목

Spike 범위를 넘지만 문서 검토 중 확인이 필요해 보인 것들입니다. 급하지 않습니다.

> **[Q-6] `job.status`를 MVP에서도 내려주십니까?**
> 작업 이력 테이블(F-JOB-02)은 12월이지만 프로세스 바(F-NAV-01)와 보관함 카드에는
> 상태값이 필요합니다. v1.7 변경 5에서 9종으로 확정된 값
> (생성됨·배치중·전처리중·원문확인·번역중·번역문확인·완료·오류·취소)을 쓰면 됩니다.

> **[Q-7] 조각 썸네일을 백엔드가 생성합니까, 프론트가 canvas로 자릅니까?**
> S2 크롭 목록(F-CRP-02)과 S3 크롭 목록 패널(F-PLC-06)에 필요합니다.
> 프론트가 자르면 원본을 다시 받아야 해서 트래픽이 커집니다.

> **[Q-8] `placement_count`는 응답에 포함됩니까?**
> F-PLC-06이 조각별 배치 횟수 표시를 요구하고, 비고에 "파생 집계"라고 되어 있습니다.
> 프론트가 배치 목록에서 세도 되지만 서버가 주면 더 안전합니다.
